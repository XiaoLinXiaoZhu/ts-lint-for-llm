# file-ts — 废弃的实验

> **状态：废弃** | 定义一种新语言格式（.fts/.tts）并不可取。此处保留文档作为历史记录，但强烈不建议参照或沿用。

## 为什么这条路走不通

FTS（File TypeScript）尝试通过"一函数一文件 + 文件名即标识符"来解决 AI 编辑代码时的定位和修改问题。但实践中暴露出根本性缺陷：

### 1. 定义前使用的顺序问题

`.fts` 文件之间天然没有文件顺序——每个函数独立成文件，编译器按需编译。但 TypeScript 工程中常见的是**函数按照调用关系从前到后排列**（尤其是启动入口），`index.ts` 作为模块出口需要手动编排导入关系。FTS 生成的 `index.ts` 虽然自动化了这一点，但缺乏对定义顺序的控制，遇到循环依赖或需要精确控制求值顺序的场景就无能为力。

### 2. import 处理不够完善

FTS 的 import 提取机制（所有 `.fts` 文件的 import 语句去重合并到 `index.ts`）过于简单：

- 无法处理条件 import / 动态 import
- 类型 import 和值 import 的混合场景容易出错
- 外部模块的 `import type` 与 `import` 在合并时会丢失语义差异

### 3. 增益不足以抵消成本

FTS 期望的"零定位成本"（文件名即函数名）在实际中并未显著优于"模块内组织良好的多个函数"。相反，它带来了：

- **额外的编译步骤**：`.fts` → `.ts`，每次修改都需要重新编译
- **工具链断裂**：IDE 支持、类型检查、调试都需要额外适配
- **上下文碎片化**：一个功能拆成十几个文件，反而丢失了模块内部的全局视野

## 真正的可取之道

这次实验的最大教训是：

> **不要发明语言级的新格式。在现有 TypeScript 框架内，代码内聚 + 拆分为小模块才是真正可取的方向。**

- **代码内聚**：相关功能放在同一个模块中，按调用顺序排列定义
- **小模块**：模块规模控制在可读范围内，但不追求"一函数一文件"的极端粒度
- **标准 import**：利用 TypeScript 已有的模块系统，而非另起炉灶

FTS 的很多设计思考（文件名即文档、SSOT、长文件名策略）本身有价值，但这些都可以在**纯 `.ts` 文件**中以更轻量的方式实现——良好的命名规范、清晰的模块边界、合理的文件结构。
